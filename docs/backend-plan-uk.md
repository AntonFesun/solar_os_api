# План бекенду Solar OS

Лише план. Цей документ не додає застосунок Next.js, розгортання MongoDB, маршрути чи скрипти початкового наповнення. Парний інтерфейс лишається на одній фікстурі в пам’яті і не викликає HTTP.

Шляхи ендпоінтів, назви полів, одиниці та рівняння балансу нижче наведені так само, як у джерелі. Пояснення — українською.

Репозиторії:

- Фронтенд: https://github.com/AntonFesun/solar_os — інтерфейс Angular. Уже існує. Одна фікстура живить кожен екран. Заглушкові значення позначені DEMO.
- Бекенд: https://github.com/AntonFesun/solar_os_api — цей план. Next.js і MongoDB з’являться тоді, коли пізніше буде зібрано реалізацію.

Спільна поверхня цього випуску — HTTP-контракт нижче. Спільної бібліотеки в цьому випуску немає.

## Межа двох репозиторіїв

`solar_os` володіє поданням: маршрутами, відтворенням теми, графіками та позначкою DEMO. Його сервіси стоять за інтерфейсами, форма яких збігається з ендпоінтами цього плану. Поточна реалізація цих інтерфейсів — клас фікстури. Фікстура тримає одну узгоджену часову лінію. Картки, діаграма потоків, аналітика, фази, батарея, сонце, вартість, сповіщення та налаштування читають той самий об’єкт. Фікстура не малює незалежні випадкові числа для кожної картки.

`solar_os_api` володітиме збереженням, валідацією, агрегацією, тарифною математикою та перевіркою енергетичного балансу. Канонічна телеметрія — вати та ват-години. Інтерфейс може форматувати kW або kWh для показу. Щойно його спрямовано на API, другого джерела істини він не тримає.

Налаштування, що впливають на ідентичність (назва, кількість фаз, ліміти, ємності, тарифи, тема), сьогодні є локальним станом фікстури. API їх зберігатиме. Тему зберігають, щоб клієнти погоджувалися між собою, а застосовує її клієнт. Уподобання одиниць показу не змінюють збережені одиниці.

Перемикання сценаріїв (день, ніч, високе навантаження, відключення мережі, розряд батареї, надлишок сонця, генератор) лишається у фікстурі фронтенду. Перша реалізація API цих сценаріїв не розміщує і рушія симуляції не нарощує. Вона віддає один засіяний майданчик, `demo-site`, чиї зразки вже задовольняють правило балансу. Коли інтерфейс пізніше викликатиме HTTP, він покаже цей seed. Керування сценарієм лишається поведінкою фікстури DEMO.

Відсутні виміри — це `null`. Нуль замість них не підставляють.

## Середовище виконання, коли буде реалізовано

Один сервіс Next.js на App Router. Фронтенд Angular у `solar_os` лишається. Route Handlers у `app/api/v1` віддають ті самі шляхи `/api/v1`. MongoDB 7, ім’я бази `solar_os`, доступ через офіційний драйвер MongoDB або mongoose. Форми колекцій живуть поруч із HTTP-шаром. Тотожність балансу, згортка вартості та сонячні співвідношення живуть у доменному шарі, який викликають Route Handlers.

Доменні області: sites, telemetry, energy, battery, solar, cost, alerts, settings.

Конфігурація процесу — `MONGODB_URI`, `PORT` і origin фронтенду для CORS. Секрети залишаються поза репозиторієм. Перша реалізація не має middleware автентифікації.

Довготривалі з’єднання з пристроями (WebSocket, MQTT, Modbus) лишаються пізнішим окремим процесом, поза цим сервісом Next.js.

`GET /api/v1/health` може повідомляти, що процес піднятий, і результат ping MongoDB. Це операційна перевірка, а не контракт інтерфейсу, і даних майданчика вона не повертає.

Зміна полів нижче, що ламає сумісність, потребує `/api/v2`. Додати поле на `/api/v1` дозволено.

## Одиниці та час

| Величина | Одиниця | Примітки |
| --- | --- | --- |
| Потужність | W | Миттєве значення |
| Енергія | Wh | Накопичена за бакет |
| Напруга | V | Фаза |
| Струм | A | Фаза |
| Коефіцієнт потужності | 0–1 | У цьому випуску лише модуль |
| Рівень заряду | 0–100 | `batterySoc` на живому зрізі та `soc` у читанні батареї — та сама величина |
| Температура | °C | `null`, коли джерело не має датчика |
| Справність | 0–100 or null | Справність батареї, коли джерело її надає |
| Гроші | decimal string | Валюта ISO 4217 з налаштувань. Для грошей двійкові числа з рухомою комою не використовують |
| Ціна тарифу | decimal string per kWh | Перетворення: kWh = Wh / 1000 у момент читання |
| Час | ISO-8601 UTC | Краї бакета — миттєвості UTC, що відповідають локальним межам майданчика |

`from` включний, `to` виключний. Обидва — миттєвості UTC. Межі бакетів вирівняні за часовим поясом IANA майданчика (типово `UTC`, зберігається на майданчику). `grain=hour` означає годину місцевого годинника. Годинний бакет тарифікують і згортають цілком; початки денного та нічного тарифів стоять на годині, тож бакет не розрізають.

## Конвенція знаків

- `consumptionW` — навантаження будинку, більше або дорівнює нулю.
- `solarW` і `generatorW` — генерація, більші або дорівнюють нулю.
- `gridW` додатне, коли майданчик імпортує з мережі, і від’ємне, коли майданчик експортує. Експорт — це від’ємна потужність мережі, а не друге живе поле.
- `batteryW` додатне, коли потужність тече в батарею (заряд), і від’ємне, коли батарея розряджається.
- Навантаження будинку не підписують як генерацію.

Енергетичні бакети розкладають знакові потоки на невід’ємні суми: `gridImport`, `gridExport`, `batteryIn` (заряд), `batteryOut` (розряд), а також `consumption`, `solar` і `generator`. Усі ці значення рядів — ват-години.

`activePower` фази використовує знак мережі. Додатне значення — імпорт на цій фазі, від’ємне — експорт. Сума активних потужностей фаз дорівнює `gridW` у межах допуску. Ця сума не є споживанням домогосподарства. Сонце і батарея можуть сидіти на шині, яку фазний лічильник не вимірює як навантаження.

## Правило балансу

Миттєва тотожність, у ватах:

`solarW + generatorW + gridW = consumptionW + batteryW`

Та сама тотожність, розкладена на невід’ємні частини:

`solarW + generatorW + max(gridW, 0) + max(-batteryW, 0) = consumptionW + max(-gridW, 0) + max(batteryW, 0)`

Допуск для зразка:

`abs(residualW) <= max(50 W, 0.02 * max(consumptionW, solarW, generatorW))`

`residualW` — ліва частина першої тотожності мінус права частина.

Інтервальна тотожність, у ват-годинах, для одного бакета:

`solar + generator + gridImport + batteryOut = consumption + gridExport + batteryIn`

Допуск для бакета:

`abs(residualWh) <= max(10 Wh, 0.02 * max(consumption, solar, generator))`

Жива відповідь містить залишок, допуск і те, чи зразок пройшов перевірку. Майбутній запис, що не проходить перевірку, відхиляють з HTTP 422, і він не замінює останній придатний зразок. Дані seed уже мають проходити перевірку. Цей випуск не зберігає ККД батареї за повний цикл заряд–розряд. Рівень заряду — виміряне поле. Розбіжність між рухом SOC та `batteryIn` / `batteryOut` лишають видимою. Мовчки її не виправляють.

`generator` є на кожній енергетичній точці, бо спільний перелік рядів однолінійної схеми його пропустив, а без нього тотожність хибна для сценарію з генератором. Фікстура теж віддає `generator`.

## Що зараз заглушено і чим володітиме API

| Питання | Фікстура фронтенду зараз | API, перша реалізація |
| --- | --- | --- |
| Джерело чисел | Один об’єкт у пам’яті. Кожне заглушкове значення позначене DEMO | MongoDB. Відповіді не позначають DEMO. Документи seed можуть записувати `source: "seed"` |
| Транспорт | Викликів HTTP немає | Ендпоінти цього плану |
| Екрани | Огляд, потік, аналітика, фази, батарея, сонце, вартість, сповіщення, налаштування | Ті самі екрани читають ці моделі читання |
| Налаштування | Лише локально: назва, фази, ліміти, ємності, тарифи, тема | `site_settings`, включно з цими полями |
| Баланс | Дані фікстури задовольняють тотожність | Сервер перевіряє тотожність на записі і повертає її на живому читанні |
| Вартість | Ті самі формули, що в цьому плані, з припущеннями | Годинні бакети, помножені на збережений тариф. Припущення повертають. Окремої цифри економії немає |
| Сповіщення | Список фікстури | Колекція `alerts`, засіяна. Рушія правил ще немає |
| Сценарії | Перемикані часові лінії DEMO | Не віддають. Один засіяний майданчик |
| Автентифікація | Немає | Немає |
| Пристрої | Немає | Немає. Адаптери — пізніша фаза |
| Порожні дані | Видимий порожній стан | Виміри `null` і `status: "empty"` |

API володіє формулами власного споживання, залежності від мережі, дисбалансу фаз, перевантаження, часу роботи батареї та вартості. Фікстура використовує ті самі формули, щоб екрани збігалися ще до появи HTTP. Інтерфейс не вигадує число економії.

## Колекції та індекси

Рядковий `siteId` — це `_id` документа майданчика. Ідентифікатор seed — `demo-site`.

### `sites`

Лише ідентичність і часовий пояс.

- `_id` (рядковий ідентифікатор майданчика), `timezone` (IANA), `createdAt`, `updatedAt`

Індекс `_id` — це пошук.

### `site_settings`

Один документ на майданчик. Це ресурс налаштувань.

- `siteId`
- `name`
- `phaseCount`: `1` або `3`
- `limits.gridImportW`, `limits.gridExportW`, `limits.voltageMinV`, `limits.voltageMaxV`, `limits.currentMaxA`, `limits.phaseImbalanceMax` (відношення від 0 до 1)
- `capacities.pvW`, `capacities.batteryWh`, `capacities.batteryReserveSoc` (0–100, лише припущення для часу роботи)
- `tariffs.currency`, `tariffs.mode` (`flat` або `dayNight`), `tariffs.importPerKwh`, `tariffs.exportPerKwh`
- `tariffs.day` і `tariffs.night`: `startLocal` на годині, плюс ціни імпорту та експорту цього вікна. `null`, коли режим — `flat`
- `theme`: `dark` або `light`
- `units.power` (`W` або `kW`) і `units.energy` (`Wh` або `kWh`), уподобання показу
- `refreshIntervalSec`, `staleAfterSec` (типово 120)
- `alertThresholds.lowBatterySoc`, `alertThresholds.highConsumptionW`
- `dataSourceMode`: `seed` до фази пристроїв

Індекс: унікальний `{ siteId: 1 }`.

### `power_samples`

Миттєва телеметрія.

- `siteId`, `ts`
- `consumptionW`, `solarW`, `gridW`, `batteryW`, `batterySoc`, `generatorW`
- `tempC`, `health` (можуть бути порожніми; читання батареї бере останній зразок)
- `status`: `ok`, `offline` або `error`

`stale` і `empty` — стани моделі читання, а не збережені статуси зразка.

Індекс: унікальний `{ siteId: 1, ts: -1 }`. Останній зразок — перший ключ у цьому порядку.

### `phase_samples`

- `siteId`, `ts`
- `phases[]`: `phase` (`L1`, `L2`, `L3`), `voltage`, `current`, `activePower`, `powerFactor`

Однофазний майданчик зберігає лише `L1`.

Індекс: унікальний `{ siteId: 1, ts: -1 }`.

### `energy_buckets`

- `siteId`
- `grain`: `hour`, `day`, `week`, `month` або `year`
- `start`: миттєвість UTC локальної межі
- `consumption`, `solar`, `gridImport`, `gridExport`, `batteryIn`, `batteryOut`, `generator` (Wh, кожне >= 0)

Індекс: унікальний `{ siteId: 1, grain: 1, start: 1 }`.

Годинні бакети — джерело для вартості, обігу та сонця за сьогодні. Бакети дня, тижня, місяця та року — суми цих годин того самого майданчика; їх зберігають, щоб запит графіка не пересумовував під час читання. Грубиші кроки ніколи не додають зверху годин, коли рахують підсумок.

### `alerts`

- `siteId`
- `severity`: `info`, `warning` або `critical`
- `type`: `high_consumption`, `phase_overload`, `voltage_anomaly`, `low_battery`, `inverter_offline`, `sensor_disconnected`, `grid_loss`
- `message`, `deviceId` (`null`, доки пристроїв немає), `raisedAt`, `resolvedAt`
- `status`: `open`, `acknowledged` або `resolved`

Індекси:

- `{ siteId: 1, status: 1, raisedAt: -1 }` для списку
- частковий унікальний `{ siteId: 1, type: 1 }`, де `status` дорівнює `open`, а `deviceId` дорівнює `null`, щоб на майданчик існувало одне відкрите сповіщення кожного типу, доки пристроїв немає

### У першій реалізації не створюють

Батарея, сонце і вартість власних колекцій не мають. Це моделі читання поверх зразків, годинних бакетів і налаштувань.

Пізніша колекція `devices` може тримати `siteId`, вид (`meter`, `inverter`, `bms`), адаптер (`rest`, `websocket`, `mqtt`, `modbus`) і статус останньої появи. Для першої реалізації її не створюють.

## Ендпоінти

Базовий шлях `/api/v1`. JSON. Невідомий ідентифікатор майданчика — 404. Відомий майданчик без вимірів — 200, зі значеннями null.

### `GET /sites/:siteId/live`

Поля відповіді:

- `siteId`
- `consumptionW`, `solarW`, `gridW`, `batteryW`, `generatorW` (число або null)
- `batterySoc` (0–100 або null)
- `status`: `ok`, `stale`, `offline`, `error` або `empty`
- `updatedAt` (ISO-8601 або null)
- `balance`: `residualW`, `toleranceW`, `ok`. Null, коли status дорівнює `empty`

Правило читання. Беруть найновіший документ `power_samples`. Немає документа — status `empty` і потужності null. Збережений `ok` стає `stale`, коли `now - ts` більше за `staleAfterSec`. Збережені `offline` і `error` проходять як є. `balance` обчислюють із повернутих чисел.

### `GET /sites/:siteId/energy`

Запит: `from`, `to`, `grain` (`hour`, `day`, `week`, `month`, `year`).

Максимальний проміжок: hour — 7 днів, day — 400 днів, week — 3 роки, month — 10 років, year — 20 років. Ширший проміжок — 400.

Поля відповіді:

- `siteId`, `from`, `to`, `grain`, `toleranceWh`
- `series[]`: `start`, `end`, `consumption`, `solar`, `gridImport`, `gridExport`, `batteryIn`, `batteryOut`, `generator`
- `summary.selfConsumption` і `summary.gridDependency` (відношення або null), плюс короткий рядок `summary.formula` для кожного

Придатний майданчик і порожній діапазон повертають `series: []` і відношення null.

`summary.selfConsumption` за діапазон — це `clamp((solar - gridExport) / solar, 0, 1)`, коли solar більше нуля, інакше null. Експорт у мережу трактують як сонце, що залишило майданчик. Енергія, якою зарядили батарею, входить у власне споживання. Ват-години генератора в чисельник не входять.

`summary.gridDependency` — це `gridImport / consumption`, коли consumption більше нуля, інакше null.

### `GET /sites/:siteId/phases/live`

Поля відповіді:

- `siteId`, `updatedAt`, `status` (те саме правило застарілості, що й для живої потужності)
- `phases[]`: `phase`, `voltage`, `current`, `activePower`, `powerFactor`
- `imbalance` (відношення або null)
- `overload` (булеве значення)

`imbalance` — це `(max(current) - min(current)) / mean(current)`, коли присутні три фази і середній струм більше нуля. Інакше null.

`overload` істинний, коли напруга будь-якої фази виходить за `voltageMinV`/`voltageMaxV`, струм перевищує `currentMaxA`, додатна `activePower` перевищує частку цієї фази в `limits.gridImportW`, модуль від’ємної `activePower` перевищує частку цієї фази в `limits.gridExportW`, або дисбаланс перевищує `phaseImbalanceMax`. Частка фази — ліміт майданчика, поділений на `phaseCount`. Порожні ліміти і порожні виміри фази не оцінюють.

### `GET /sites/:siteId/battery`

Поля відповіді:

- `siteId`
- `soc`, `capacityWh`, `powerW`, `throughputWh`, `tempC`, `health`
- `runtime.hours` (число або null), `runtime.assumption` (рядок, присутній завжди)
- `updatedAt`

`soc`, `powerW`, `tempC` і `health` беруть з останнього зразка потужності. `capacityWh` і `batteryReserveSoc` беруть з налаштувань. `throughputWh` — сума `batteryIn + batteryOut` лише по годинних бакетах. Значення null, коли годинних бакетів немає.

`runtime.hours`, лише поки `powerW` від’ємне, `capacityWh` більше нуля і `soc` більше або дорівнює `batteryReserveSoc`:

`(soc - batteryReserveSoc) / 100 * capacityWh / abs(powerW)`

Припущення, яке повертають текстом: останню потужність розряду тримають сталою; сонце, мережу, генератор і пізніші зміни навантаження ігнорують; резервний SOC беруть з налаштувань; результат null, коли батарея не розряджається, ємність дорівнює нулю, `soc` є null або `soc` нижчий за `batteryReserveSoc`.

### `GET /sites/:siteId/solar`

Поля відповіді:

- `siteId`, `powerW`, `todayWh`, `peakW`, `exportWh`, `selfConsumption`
- `assumptions` (масив рядків)
- `updatedAt`

`powerW` — останній зразок. `todayWh` і `exportWh` сумують годинні бакети місцевого сьогодні (`solar` і `gridExport`). `peakW` — максимум `solarW` серед зразків цього місцевого дня. Кожне значення null, коли відповідних рядків немає. `selfConsumption` використовує відношення, визначене вище, для місцевого дня. Масив припущень стверджує, що експорт відносять до сонця, що заряд батареї входить у власне споживання, і що енергію генератора з чисельника виключають.

### `GET /sites/:siteId/cost`

Запит: `from`, `to` (ті самі включно-виключні миттєвості UTC).

Поля відповіді:

- `siteId`, `from`, `to`
- `tariff`: збережений тариф, відлунений назад (валюта, режим, ціни, вікна, часовий пояс)
- `importCost`, `exportCredit` (десяткові рядки)
- `assumptions` (масив рядків)

Вартість використовує годинні бакети, чий `start` потрапляє в `[from, to)`. Кожен бакет бере ціну вікна, що містить його початок. Режим flat використовує плоскі ціни.

- `importCost = Σ (gridImport / 1000) * import price`
- `exportCredit = Σ (gridExport / 1000) * export price`

Імпорт і експорт не згортають у нетто. Список припущень називає режим, ціни, часовий пояс і рішення не рахувати економію. У цього ендпоінта поля економії немає.

### `GET /sites/:siteId/alerts`

Необов’язковий запит: `status`, `limit` (типово 50, максимум 200). Фікстура може зігнорувати запит і повернути свій повний список DEMO.

Поля відповіді: `siteId`, `alerts[]` з `id`, `severity`, `type`, `message`, `deviceId`, `raisedAt`, `resolvedAt`, `status`. Сортування — `raisedAt` за спаданням.

Перша реалізація повертає засіяні сповіщення. Пороги вона не оцінює. Пороги зберігають для пізнішого оцінювача. Передбачені типи, коли цей оцінювач з’явиться: високе споживання проти `highConsumptionW`, перевантаження фази та аномалія напруги за правилами фаз, низький заряд проти `lowBatterySoc`, а також інвертор офлайн, від’єднаний датчик і втрата мережі зі статусу адаптера.

### `GET /sites/:siteId/settings` і `PATCH /sites/:siteId/settings`

GET повертає повний документ налаштувань.

PATCH приймає частковий JSON-об’єкт з полів налаштувань, перелічених вище. Невідомі ключі — 400. `dataSourceMode`, відмінний від `seed`, — 400 до фази пристроїв. Відповідь — повний документ після запису. PATCH не переписує зразки чи бакети. Зміна ємності впливає лише на подальшу математику часу роботи. Тему зберігають; застосовує її клієнт.

## Помилки

| Статус | Коли |
| --- | --- |
| 400 | Некоректні `from`/`to`/`grain`, проміжок понад стелю, невідоме поле PATCH, `dataSourceMode` ще не дозволений |
| 404 | Невідомий `siteId` |
| 422 | Майбутній запис зразка або бакета, що не проходить тотожність балансу |

Поля тіла помилки: `statusCode`, `error`, `message`, `details`. Відмови балансу містять `details.residualW` або `details.residualWh`.

## Фази

Це завдання — сам план. Код застосунку разом із ним не постачається.

Перша реалізація, пізніше: сервіс Next.js на App Router, колекції та індекси вище, seed `demo-site`, що проходить правило балансу, ендпоінти читання, PATCH налаштувань, правило застарілості на читанні та CORS для origin фронтенду. Автентифікації та вводу-виводу пристроїв усе ще немає.

Автентифікація — пізніша фаза. Вона додає користувачів і членство в майданчику і вимагає облікових даних на кожному маршруті, крім health. Спільний статичний секрет цю фазу не замінює.

Адаптери пристроїв — пізніша фаза. Вони лише приймають дані. Набір адаптерів: REST poll, WebSocket, MQTT, Modbus, smart meter, inverter і BMS. Довготривалі з’єднання (WebSocket, MQTT, Modbus) лишаються окремим процесом, поза сервісом Next.js. Вихід адаптера — зразок потужності і, коли лічильник має фази, зразок фаз. Обидва проходять перевірку балансу перед вставкою. Шляху команд до пристроїв немає. Моніторинг і керування лишаються окремо.

## Поза обсягом

- Застосунку Angular у репозиторії API немає, і другого репозиторію фронтенду немає.
- Клієнтів хмар виробників немає, і команд пристроям немає.
- Вигаданої економії немає, і мовчазного переписування SOC, щоб примусити кулонівський баланс, немає.
- Випадкових даних на кожну картку немає. Одна часова лінія майданчика живить кожну модель читання.
